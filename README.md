# WHERE FOOD — 근거 기반 식사 추천 MVP

Flask + Vanilla JS로 자연어 → 제약 JSON → **사용자 확인·수정** → 서버 재검증 → 실제 장소/메뉴 조회 → 규칙 필터 → 최대 3곳 → 선택 기록을 연결합니다.
자연어 해석과 근거 요약은 **Ollama + Qwen3.5 9B 로컬 모델만** 사용합니다. 숫자·필수 조건 판정·정렬은 서버 코드가 수행합니다. Qwen의 제한형 RAG 설명은 서버 검증 후에만 표시하고, 실패하면 기존 템플릿을 사용합니다.
OpenAI 호출 코드와 SDK 의존성을 제거했습니다. 공용/프로젝트 전용 OpenAI 키가 있어도 사용하지 않으며, 외부 LLM 자동 전환도 없습니다.

해석과 검색은 별도 API입니다. 확정 검색은 **LangGraph**가 위치 재질문·추천·결과 없음으로 분기하며, 기존 검색·필터·정렬 함수를 그대로 사용합니다.
**LLM만 로컬**입니다. 카카오 장소·지도·경로, 선택적 날씨 조회와 웹 폰트 등은 네트워크를 사용합니다.

## 실행

Python 3.11 이상을 사용합니다. 기존 `venv`는 Python 3.9/3.11 경로가 섞여 있어 새 `.venv`를 사용합니다.

### 1. Ollama와 모델 준비

[Ollama](https://ollama.com/download)를 설치합니다. macOS에서는 GPU 사용을 위해 네이티브 앱/CLI 실행을 권장합니다.
터미널 하나에서 클라우드 기능을 끈 로컬 서버를 실행합니다. 이미 Ollama가 해당 포트에서 실행 중이면 서버를 중복 실행하지 말고 해당 실행 방식에 클라우드 차단 설정을 적용한 후 재시작하세요.

```sh
OLLAMA_NO_CLOUD=1 OLLAMA_HOST=127.0.0.1:11434 OLLAMA_NUM_PARALLEL=1 OLLAMA_MAX_LOADED_MODELS=1 ollama serve
```

다른 터미널에서 모델을 준비합니다. `qwen3.5:9b`는 약 6.6GB 다운로드이며 실행 메모리는 추가로 필요합니다. 기존 모델을 삭제할 필요는 없습니다.

```sh
OLLAMA_HOST=127.0.0.1:11434 ollama pull qwen3.5:9b
curl --noproxy '*' http://127.0.0.1:11434/api/tags
```

macOS Ollama 앱으로 실행하는 경우 `launchctl setenv OLLAMA_NO_CLOUD 1` 설정 후 앱을 재시작합니다.
Flask의 `.env`에 `OLLAMA_NO_CLOUD=1`만 추가해도 **이미 실행 중인 Ollama 서버에는 적용되지 않습니다**.
모델 이름과 URL은 코드에 고정되어 `OLLAMA_HOST`, `OLLAMA_MODEL`, OpenAI 관련 환경변수로 바뀌지 않습니다.
로컬 HTTP 클라이언트는 환경 프록시·자동 인증·리디렉션을 사용하지 않습니다. `:cloud` 모델이나 외부 LLM API로 재시도하지 않습니다.

### 2. Flask 실행

프로젝트 루트에서 실행합니다. 이미 `.venv`가 있으면 생성 단계는 생략할 수 있습니다.

```sh
python3.11 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python scripts/import_menu_data.py
.venv/bin/python app.py
```

http://127.0.0.1:8000 에서 실행됩니다. `.env`에 `.env.example`의 설정을 반영하세요. 기존 키를 덮어쓰지 마세요.

- 공용 `OPENAI_API_KEY`는 사용하지 않습니다. 기존 환경변수와 `.env`의 키도 변경하지 않습니다.
- 이전 `WHERE_FOOD_ENABLE_OPENAI`, `WHERE_FOOD_OPENAI_API_KEY`, `WHERE_FOOD_OPENAI_MODEL` 설정은 더 이상 읽지 않습니다.
- `WHERE_FOOD_OLLAMA_TIMEOUT_SECONDS`: 기본 `120`, 허용 범위 `1~300`. 모델 첫 로딩이 느린 경우에만 조정합니다. 연결 제한은 3초입니다.
- `WHERE_FOOD_RAG_TIMEOUT_SECONDS`: 설명 호출의 읽기 timeout, 기본 `30`, 허용 범위 `1~60`. 설명 실패는 추천 실패가 아니라 템플릿 전환입니다. 별도 연결 제한은 3초이며 전체 추천 시간의 상한은 아닙니다.
- `KAKAO_REST_API_KEY`: 장소·좌표·도보 경로 조회용.
- `KAKAO_JAVASCRIPT_KEY`: 지도 표시용 공개 앱 키. 카카오 개발자 설정에 사용하는 로컬 도메인을 등록하세요.
- `WEATHER_API_KEY`: 선택. 날씨 실패는 식당 추천을 막지 않습니다.
- `FLASK_SECRET_KEY`: 지속적인 랜덤 값. 미설정 시 프로세스마다 임시 키가 생겨 재시작 후 이전 세션 기록과 확인 중인 초안을 사용할 수 없습니다. 운영/여러 worker는 동일한 값 필요.
- `DATABASE_PATH`: 기본 `instance/where_food.db`. `instance/`는 Git에서 제외합니다.
- `COOKIE_SECURE=1`: HTTPS로 서비스할 때 설정합니다.

`GET /api/health`는 `/api/tags`로 서버 연결·정확한 모델 설치 여부를 확인하여 `parser.provider`, `parser.model`, `parser.ready`, 모델 `digest` 또는 실패 코드를 반환합니다. 추론을 실행하거나 모델을 로딩하지 않습니다.
`ready=true`는 모델 설치 확인이지 메모리 여유·추론 성공·의미 정확성을 보증하지 않습니다. 카카오 키는 설정 여부만 표시합니다.
`.env` 설정을 변경했다면 Flask 서버를 재시작하세요.

### 3. 식당 API 없이 로컬 추출만 확인

```sh
.venv/bin/python scripts/evaluate_parser.py --query '강남역에서 도보 10분, 1만 5천 원 이하, 얼큰한 국물인데 땅콩은 빼고 조용한 곳'
.venv/bin/python scripts/evaluate_parser.py
.venv/bin/python scripts/evaluate_parser.py --split dev --output instance/parser-dev.json
.venv/bin/python scripts/evaluate_parser.py --split holdout --output instance/parser-holdout.json
```

첫 명령은 검증된 제약 JSON을 출력합니다. 두 번째는 수작업 정답 40문장에 대해 필드별 불일치, 통과 수, p50/p95 시간을 출력합니다.
개발 20문장과 별도 검증 20문장을 분리했습니다. 프롬프트는 개발 세트로만 수정하고 검증 결과는 그대로 기록합니다.
정답 비교에서 목록 순서만 무시하고, 누락·임의 추가·알레르기 오인식은 실패로 집계합니다. 실패가 있으면 종료 코드 1입니다.
모델 로딩 시간은 첫 사례 시간에 포함됩니다. 40문장으로 일반적인 한국어 정확도나 알레르기 안전성을 보증하지 않습니다.
미지원·충돌 조건은 `unknown_terms`가 비어 있지 않아야 통과합니다. 그 외 필드도 정답과 일치해야 하며 단순 파싱 오류를 성공으로 세지 않습니다.
이 스크립트는 **카카오·날씨 API를 호출하지 않고 앱 DB에 쓰지 않습니다**. `--limit 1`로 한 문장부터 확인할 수 있습니다.

기존 날씨 모델의 카테고리 힌트를 켜려면 추가 설치합니다.

```sh
.venv/bin/python -m pip install -r requirements-model.txt
```

기존 모델은 2019–2020년 집계 기반 참고 점수이며 선택 확률이 아닙니다. 실제 관측이 있을 때만 아래 정책의 최종 동점 결정에 사용합니다.
모델·의존성 또는 날씨가 없으면 추천은 계속되고 `weather_score=null`, `weather_applied=false`로 표시합니다.
날씨 카드는 초단기실황의 강수형태(`PTY`)를 사용합니다. 이 API는 하늘상태(`SKY`)를 제공하지 않으므로 강수형태가 0이면 **강수 없음**으로 표시하며, 맑음으로 추정하지 않습니다. 강수형태도 누락/미지원이면 **날씨 상태 미확인**으로 구분합니다.
기존 모델 파일은 보존했고 Windows 절대 경로와 회귀 모델 저장 파일명 오타를 수정했습니다. 9/9 코드 검토에서는 과거 분류 학습의 정답 유출 통계 피처와 단일 조합 GridSearch를 제거했습니다. 아래 스크립트는 별도 성능 평가 없이 학습만 하며, 날씨 회귀 모델은 집계 기반 참고 점수를 근사할 뿐 사용자 선택을 예측하지 않습니다.
아래는 **재학습을 원할 때만** 실행합니다. 이 변경에서 기존 모델을 재학습하거나 덮어쓰지는 않았습니다.

```sh
.venv/bin/python train_regression_model.py --help
.venv/bin/python RandomForestClassifier.py --help
# 기본 CSV/출력은 작업 디렉터리가 아닌 스크립트 위치 기준. 다른 출력으로 보존 가능:
.venv/bin/python train_regression_model.py --data /path/to/data.csv --output /path/to/new-model.pkl
```

기본 회귀 출력은 `model/weather_food_regression_model3.pkl`, 분류 출력은 `model/weather_food_final_model2.pkl`입니다.
Selenium과 공용 `result.png` 생성은 웹 요청 경로에서 제거했습니다.

따라서 예제의 땅콩 제외 조건은 결과 없음이 정상이며, 일반 메뉴로 자동 완화하지 않습니다.

먼저 “강남역에서 1만 5천 원 이하 식당”으로 확인하고, 식재료/분위기 근거를 확보한 후 더 복잡한 조건을 검증하세요.
메뉴 데이터는 자동 수집·자동 갱신하지 않습니다.

CSV의 `menu_evidence`는 다음 JSON을 셀 안에 넣습니다. `observed_on`은 실제 확인일 또는 출처의 사실 기준일입니다.

```json
{
  "title": "매장 공식 메뉴 또는 확인 기록",
  "url": "https://example.com/actual-menu-evidence",
  "observed_on": "2026-09-07",
  "excerpt": "해당 메뉴명과 1인 메뉴 가격을 입증하는 짧은 원문"
}
```

`tags`, `absent_ingredients`, `atmosphere`는 각각 `[{"term": "...", "evidence": {...}}]` 형식입니다.
`allergy_checks`는 여기에 `cross_contact_checked`가 추가됩니다. 식당의 해당 성분 미사용과 교차접촉 관리에 대한 명시적 확인 기록이 있을 때만 true입니다.
재료 목록에 이름이 없다는 사실, 메뉴명에서의 추정, 블로그 추측은 미사용/알레르기 근거가 아닙니다.
빈 배열은 **미확인**입니다. 단순 기피 재료와 알레르기는 구분하고, 알레르기는 방문 전 재확인을 안내합니다.
실제 가격이 없는 경우 `price_krw`를 비워 두면 저장할 수 있지만 추천 후보로는 통과하지 않습니다.

CSV에 선택 열 `dietary_checks`, `opening_status`를 추가할 수 있습니다. 기존 CSV는 그대로 가져올 수 있습니다.

- `dietary_checks`: `[{"term":"vegan","evidence":{...}}]`. `term`은 `vegan`, `vegetarian`, `pescatarian` 중 하나입니다.
- 비건은 동물성 재료 제외, 채식(`vegetarian`)은 육류·생선·해산물 제외 및 달걀·유제품 허용, 페스코는 육류 제외 및 생선·해산물·달걀·유제품 허용입니다. UI에도 정책을 표시합니다.
- 요청 식단과 일치하는 명시적 근거가 있어야 통과합니다. 메뉴명이나 재료 목록의 누락으로 추정하지 않으며 식단 확인을 알레르기 확인으로 대체하지 않습니다.
- `opening_status`: `is_open`(boolean), `provider`(`official` 또는 `merchant_confirmed`), `observed_at`, `valid_until`(시간대 포함 ISO 시각), `evidence`로 구성된 JSON 객체입니다. 빈 셀은 미확인입니다.
- 영업 기록은 실제 확인 후 신뢰하는 운영자가 가져오는 자료입니다. 출처 URL이나 provider 문자열 자체가 진위를 자동 검증하지는 않습니다. 공개 리뷰나 단순 장소 존재 여부는 근거로 등록하지 않습니다.
- 영업 기록의 유효 창은 최대 15분입니다. 미래 확인 시각·만료·휴무·확인 누락은 '지금 영업 중' 요청에서 제외합니다. 같은 식당의 여러 메뉴에 기록이 있으면 최신 기록을 사용하고 같은 시각의 상충 기록은 미확인 처리합니다.
- 자동 실시간 영업 데이터 제공자는 아직 연결하지 않았습니다. 실제 자료가 없는 초기 데이터에 예시 영업/식단 근거를 넣지 않았습니다. 이번 6일 범위에서는 수집을 확대하지 않습니다.

데이터 반영은 `(place_id, menu_name)` 단위 upsert이며 다른 메뉴·사용자 기록은 삭제하지 않습니다.
원하는 경우 `--database /path/to/file.db`로 별도 DB를 지정할 수 있습니다.

## API 계약

1. `POST /api/constraints`: 로컬 Qwen 해석과 원문 검증만 수행합니다. 식당 검색이나 추천 기록 저장은 하지 않습니다.

```json
{"query": "강남역에서 15000원 이하"}
```

응답의 `constraints`를 편집 화면에 표시하고 `unknown_terms`를 별도로 안내합니다. `draft_token`은 현재 익명 세션에 연결된 **30분 유효 서명 토큰**입니다. 서명은 암호화가 아니므로 토큰을 URL·로그·외부 서비스에 넣지 마세요. UI는 메모리에만 보관하며 새로고침/원문 수정 시 폐기합니다.

2. `POST /api/recommend`: 사용자가 확정한 값을 재검증한 뒤 검색합니다. **기존 query-only 요청과 호환되지 않습니다.** 토큰은 같은 쿠키 세션에서 사용해야 합니다.

```json
{
  "draft_token": "해석 응답의 draft_token",
  "confirmed": true,
  "constraints": {
    "location_text": "강남역",
    "budget_krw": 10000,
    "walking_minutes_max": null,
    "max_distance_m": null,
    "excluded_ingredients": [],
    "allergens": [],
    "dietary_requirements": [],
    "open_now": false,
    "excluded_foods": [],
    "dish_tags": [],
    "atmosphere_tags": [],
    "hard_fields": []
  },
  "ignored_unknown_terms": [],
  "lat": null,
  "lon": null,
  "origin_place_id": null
}
```

확인 화면의 장소가 좌표보다 우선입니다. 위치 결과가 여러 개면 `clarification_required`와 `location_options`를 반환합니다.
선택된 ID를 동일 토큰·확정 조건과 함께 `origin_place_id`로 보내면 서버가 위치 후보를 다시 대조합니다. **장소 재선택·예산 수정에는 LLM을 다시 호출하지 않습니다.** 장소 없는 조건에는 lat/lon이 필요합니다.

예산·도보·직선거리는 각각 1~1,000,000원 / 1~120분 / 1~20,000m 정수 또는 null입니다. 숫자 문자열·소수·boolean 대용 값은 거부합니다. 장소는 최대 200자, 목록은 중복 없이 각 20개/항목 50자까지입니다. 식단·필수 선호는 허용된 값만 받습니다.
사용자는 **조건**만 수정할 수 있고 메뉴 가격·출처·추출 원문 근거·추천 순위 등의 **사실**은 넣을 수 없습니다. 수정 값은 원문 추출값으로 위장하지 않고 `confirmation.source=user_confirmed`, `edited_fields`로 구분합니다.
미지원 조건은 토큰에 보존되며 JSON에서 지운다고 사라지지 않습니다. 원문을 고쳐 다시 해석하거나, UI에서 항목별로 명시적으로 제외하면 `ignored_unknown_terms`에 들어갑니다. 원래 없던 항목의 제외 요청은 거부합니다. 알레르기 등 조건을 서버가 자동 완화하지 않습니다.
조건 수정 후에는 확인 체크를 다시 해야 합니다. 진행 중 입력을 바꾸면 이전 화면 결과와 행동 대상이 지워지고 늦게 도착한 성공/오류 응답을 무시합니다.

추천 응답에는 `schema_version=3`, `ranking_version=rules-v2`, `request_id`, `parser`(공급자·모델·파서 버전), `constraints`, `origin`, `status`, `recommendations`, `diagnostics`, `confirmation`, `workflow`, `next_action`이 들어갑니다. 설명 단계 실행 시 `rag`와 후보별 `explanation`이 추가됩니다.
추천 항목에는 장소 정보, 대표 메뉴·가격·출처, 충족 조건의 근거, 미확인 선호, 조회 시각, 경로가 들어갑니다.
새 제약은 `dietary_requirements`(목록), `open_now`(boolean)입니다. 파서 버전은 `qwen3.5-9b-v2`입니다.
카드의 `score_breakdown`에는 `hard_constraints`, `soft_matches`, `evidence_completeness`, `evidence_age_days`, `weather_category`, `weather_score`, `weather_applied`가 포함됩니다.
`opening_status`에는 유효한 영업 확인 기록 또는 null, `weather_context`에는 날씨 출처·관측 시각 또는 이용 불가 이유가 들어갑니다.

상태:

- `ok`: 3곳 확인
- `partial`: 1~2곳 확인. 조건 미충족 식당으로 3곳을 채우지 않음
- `no_results`: 검색 범위/확보 데이터에서 확인된 후보 없음
- `clarification_required`: 위치 선택·모호하거나 현재 지원하지 않는 조건 확인 필요

HTTP 오류는 JSON의 `error`, `code`로 반환합니다.

| HTTP / code | 뜻 / 조치 |
| --- | --- |
| 400 / `invalid_input` | 입력 형식 확인 |
| 400 / `invalid_draft` | 위조·다른 세션의 토큰. 다시 해석 |
| 409 / `draft_expired` | 초안 30분 만료. 다시 해석 |
| 422 / `parse_failed` | JSON 불완전·스키마 오류·원문/숫자 불일치. 문장을 명확히 수정 |
| 429 / `parser_busy` | 같은 Flask 프로세스의 이전 추론이 진행 중. 완료 후 다시 시도 |
| 503 / `ollama_unavailable` | Ollama 실행·버전·메모리 확인 |
| 503 / `ollama_model_missing` | `ollama pull qwen3.5:9b` 실행 |
| 503 / `parser_not_configured` | 프로젝트 전용 timeout 설정 확인 |
| 504 / `ollama_timeout` | 모델 로딩·메모리·timeout 확인. 자동 재시도 없음 |

파서 관련 오류는 `/api/constraints`에서 발생합니다. 기존 장소·경로·DB 장애도 503으로 반환합니다. Ollama는 `think=false`, `temperature=0`, 컨텍스트 8192, 출력 상한 2048토큰으로 호출합니다.
최종 완료된 JSON만 처리하고, 잘린 출력·중복 원문 근거·잘못된 숫자를 통과시키지 않습니다. 설정은 문장 단위 추출의 초기값이며 품질·속도 측정 후 조정하세요.
추론 후 모델은 기본 5분간 메모리에 유지합니다. 입력 수정으로 브라우저 요청을 취소해도 서버 추론이 즉시 중단되는 것은 아닙니다.

`POST /api/events`:

```json
{
  "id": "이벤트 UUID",
  "request_id": "추천 응답의 UUID",
  "event_type": "restaurant_selected",
  "place_id": "실제로 노출된 식당 ID"
}
```

종류는 `recommendations_viewed`, `restaurant_selected`, `restaurant_rejected`, `detail_clicked`, `directions_clicked`입니다.
노출 이벤트는 place_id=null, 나머지는 실제 추천한 장소만 허용합니다. 순위와 세션 ID는 서버에서 결정합니다.
같은 이벤트 ID 재시도는 중복 저장하지 않습니다. 다른 세션/다른 요청의 식당에 대한 임의 선택 기록은 거부합니다.
원문·정확한 시작 좌표·좌표가 들어간 경로 링크는 저장 스냅샷에서 제거합니다. 메뉴·추출 조건·노출 후보·순위·출처·행동은 보존합니다.
클릭은 방문/주문이나 최종 선택의 정답으로 자동 간주하지 않습니다.

## 필터·정렬 정책

1. 알레르기·식단 → 제외 재료/음식 → 가격 확인·예산 → 거리 → 현재 영업 → 필수 특성/소프트 선호 순 검사
2. 필수 사실의 출처가 없거나 현재 기준 90일을 넘으면 통과시키지 않음. 영업 상태는 별도의 최대 15분 유효 창 적용
3. 도보 조건은 실제 경로 API의 초 단위 예상 시간으로 검사. 600초는 통과, 601초는 제외. 식당당 한 번 조회
4. 하드 조건 통과 메뉴만 **소프트 선호 일치 수 → 근거 완성도 → 근거 최신성 → 거리 → 날씨 점수** 순으로 정렬
5. 거리 비교는 도보 조건이 있으면 예상 도보 시간, 없으면 직선거리. 날씨까지 동점이면 가격 → 장소 ID → 메뉴명으로 결정
6. 정렬 후 식당별 가장 높은 메뉴 하나를 남겨 최대 3곳 반환

근거 완성도는 메뉴/가격·음식 특성·분위기·식단·미사용 성분·교차접촉 확인·유효 영업 상태의 7개 항목 중 신선한 근거가 있는 비율입니다.
같은 항목에 기록을 중복해도 가산하지 않습니다. 이 값은 **정보 확보 비율이지 안전 확률이 아닙니다**.
최신성은 이번 결정에 사용한 근거 중 가장 오래된 날짜의 경과 일수이며 낮을수록 우선합니다.
날씨는 서버가 실제 검색 기준 좌표에서 관측을 조회하고 카카오 카테고리를 기존 모델 카테고리에 대응시킵니다.
앞선 기준이 같은 그룹의 모든 후보에 유효 점수가 있을 때만 동점을 결정합니다. 누락·미지원 카테고리에 0점이나 0℃를 만들어 넣지 않습니다.

검색은 기본 2km, 가까운 음식점 최대 45곳 + 현재 메뉴 카탈로그 최대 6개 상호의 검색 결과(각 5개)를 합칩니다.
검색·태그는 범위가 제한된 MVP입니다. 데이터가 늘면 지역별 카탈로그 인덱스와 검색 재현율을 먼저 개선하세요.
해석 단계의 가격·거리 숫자는 원문 단위를 서버에서 다시 계산합니다. 사용자 수정값은 원문과 같도록 강제하지 않고 타입·범위·필수 값의 일관성을 재검증합니다. 스키마 형식이 맞아도 LLM의 의미 추출 정확성은 별도 평가가 필요합니다.
특정 미래 시각의 영업시간·할랄/키토 등 미지원 식단·복합 OR·전체 인원 예산 등은 파서가 `unknown_terms`로 남겨 재질문합니다. 자동 조건 완화는 하지 않습니다.
알레르기 기록은 안전 보증이 아닙니다. 누락 근거를 만들어 추천하지 않습니다.

## 9/8 구현: 해석·검색 분리 + 최소 LangGraph

요청한 1·2일차 범위를 구현했습니다. 자연어 해석은 별도 엔드포인트이고, 그래프는 **확정된 조건 이후**의 분기를 담당합니다.

```text
POST /api/constraints → 확인·수정 화면
POST /api/recommend → 재검증 → RESOLVE
```

## 작은 RAG 설명 생성과 실습

현재 `meal-v2` 그래프는 추천 후보가 있을 때만 `EXPLAIN`을 실행합니다.

1. 기존 카카오 위치 검색으로 후보를 찾습니다.
2. 기존 `db.get_menus()` SQL 조회로 후보 ID에 연결된 메뉴·가격·출처를 가져오고 필터·순위를 확정합니다.
3. 해당 조회 결과 중 Top 3의 근거만 Qwen에 전달합니다. 재조회로 가격이 달라지지 않도록 같은 스냅샷을 재사용합니다.
4. Qwen이 메뉴/가격 문장을 반드시 포함해 식당별 1~3문장을 선택·배열합니다. 서버가 식당 ID·문장·출처 ID를 대조한 뒤 카드에 **Qwen 근거 요약**을 표시합니다.
5. 실패하면 **AI 요약을 사용하지 못해 기존 근거 설명을 표시합니다**라는 안내와 기존 메뉴·조건 일치·출처 카드를 그대로 보여줍니다.

이는 **구조화 SQL 검색을 사용하는 제한형·추출형 RAG**입니다. 자유로운 의역/작문이나 임베딩 기반 검색이 아닙니다. 모델은 검색된 근거에 연결된 서버 문장만 선택할 수 있습니다. 가격·거리·알레르기 판정·순위를 모델에 맡기지 않습니다. 사용자 원문, 좌표, 토큰, 전체 DB는 설명 프롬프트에 넣지 않습니다.

안전/실패 정책:

- 식당별 출처 ID와 문장이 정확히 일치해야 합니다. 다른 식당의 출처, 임의 사실/가격/URL, 중복·누락·재정렬된 식당, 잘린 JSON은 전체 설명 배치의 검증 실패입니다. 거절된 생성문은 응답/DB에 저장하지 않습니다.
- 출처는 검토하여 가져온 SQL 기록을 신뢰합니다. URL을 자동 방문해 원문 진위까지 재검증하는 기능은 아닙니다. 문장 대조 성공률을 사실의 진실성이나 알레르기 안전 보증으로 해석하지 마세요.
- 해석과 설명은 같은 프로세스 내 추론 잠금을 공유합니다. 이미 모델을 사용 중이면 설명은 대기/재시도 없이 템플릿으로 전환합니다. 해석 단계의 기존 동시 요청 정책은 유지합니다.
- 한 번에 최대 3곳·식당별 최대 6개 근거만 전달합니다. 직렬화한 근거가 UTF-8 12KB를 넘으면 모델을 호출하지 않습니다. 이는 컨텍스트 크기를 제한하는 간단한 기준이지 정확한 토큰 계산이 아닙니다.
- 모델 미실행/미설치/timeout·잘못된 설명 설정도 템플릿으로 복귀합니다. 새 API 키, 외부 LLM, 벡터 DB, 크롤러는 추가하지 않았습니다.
- 생성 전후에 출처의 90일 유효기간과 영업 기록을 다시 검사합니다. 생성 중 필수 근거가 만료되면 후보를 제외하고 남은 순서를 유지합니다. 모두 제외되면 `NO_RESULTS`로 갑니다. 만료일을 최신으로 바꾸거나 새 후보로 채우지 않습니다.
- 재질문/검색 결과 없음에는 설명 모델을 호출하지 않습니다. 위치 재선택·조건 수정 시 **조건 해석**은 반복하지 않지만, 새 추천 결과에 대한 **설명 추론**은 수행할 수 있습니다.

추가 응답 필드:

```json
{
  "rag": {
    "version": "sql-extractive-v1",
    "method": "qwen_grounded",
    "model": "qwen3.5:9b",
    "retrieval": "kakao_candidates_then_sql_menu_evidence",
    "attempted": true,
    "fallback_reason": null,
    "evidence_count": 4,
    "duration_ms": 0
  }
}
```

위 숫자는 형식 예시입니다. `duration_ms`는 실행 시 측정합니다. 후보별 `explanation`은 `method`, `version`, `fallback_reason`, `sentences: [{text, source_id}]`, `sources: [{source_id, title, url, observed_on, excerpt}]`입니다. ID는 해당 추천 근거 목록 안에서 대조하며 장기 불변 ID는 아닙니다. 템플릿 모드에서는 `sentences/sources`가 빈 배열이고 기존 `matches/menu.source`를 사용합니다. 요청 스냅샷에 검증된 설명과 전환 사유를 보존합니다.

실습:

1. Ollama는 그대로 실행하고 Flask 서버를 재시작합니다: `.venv/bin/python app.py`. `.env` 수정은 필수가 아닙니다.
2. `강남역에서 15000원 이하` → 해석 → 예산을 10,000원으로 수정 → 확인 체크 → 검색 → 강남역 위치 선택.
3. 카드의 **Qwen 근거 요약**과 출처, `RESOLVE → SEARCH_FILTER_RANK → EXPLAIN → RESPOND`를 확인합니다.
4. 예산을 1원으로 바꾸면 `NO_RESULTS`이며 설명 모델은 실행하지 않습니다.
5. 장애 실습은 초안을 만든 **뒤에** 직접 실행한 Ollama 서버를 종료하고 검색합니다. 장소/메뉴 데이터가 정상이라면 추천은 유지되고 템플릿 안내가 나타납니다. 끝나면 Ollama를 다시 실행하세요. 모델만 언로드하면 자동 재로딩되므로 서버 중단과 다릅니다.

```sh
.venv/bin/python -m unittest discover -s tests -v
node test_recommend_flow.js
```

모의 테스트에서 SQL 근거 연결, 가격/출처/식당 변조, 안전 보증·프롬프트 지시문 삽입, 응답 잘림, 모델 장애, 잠금/컨텍스트 제한, 생성 중 영업 기록 만료, 화면의 출처·텍스트 렌더링과 템플릿 복귀를 검사합니다. 자동 테스트에서 외부 API나 실제 추론을 호출하지 않습니다.

이번 RAG 변경의 검증: 백엔드 50개 테스트와 JS 검사 통과. 실제 로컬 Qwen + 카카오 + 임시 DB의 HTTP 흐름에서 자루우동 7,000원·비빔밥 8,000원의 요약과 출처 대조가 통과했습니다. 이 2곳 설명 호출은 약 11.7초(1회 측정; 일반 성능 보장 아님)였습니다. 설명 호출에만 timeout을 모의 주입한 경우에도 같은 후보·가격·순위와 기존 근거 카드를 유지했고, 1원 예산의 결과 없음에서는 설명 호출을 건너뛰었습니다. 원래 DB·CSV·모델·실행 중인 Ollama는 보존했습니다.
Chrome의 임시 서버 화면에서도 조건 수정 → 장소 선택 → `EXPLAIN → RESPOND`와 두 식당의 Qwen 요약·출처 링크 표시를 확인했습니다. 지도 SDK가 로드되지 않는 테스트 주소에서는 기존 목록 대체 화면을 사용했습니다.

## 후보별 선택 예측 RandomForest: 오프라인 학습·비교

기존 날씨 카테고리 모델과 별개인 **이진 선택 예측 모델**입니다. 기존 SQLite 요청 스냅샷과 이벤트를 재사용합니다. 새로운 DB 테이블, 외부 API, 데이터 수집, 웹 요청 중 모델 학습/로딩은 추가하지 않았습니다. **운영 추천은 계속 `rules-v2`**입니다.

```text
기존 하드 필터 → 규칙 Top 3 → RAG/유효기간 재검사 → 응답 스냅샷 + 노출/선택 이벤트
                                                        ↓ 읽기 전용
                           후보별 특징/선택 라벨 → 요청 시간순 분할 → RF 학습
                                                        ↓
                           같은 평가 후보의 규칙 순위 vs RF 순위 → 보고서
```

범위와 라벨 정책:

- 현재는 **실제로 표시한 하드 필터 통과 후보 2~3곳 사이의 재정렬 비교**입니다. 검색된 20~75곳 전체를 비교하는 모델이 아닙니다. 표시하지 않은 후보에는 선택 기회가 없었으므로 음성 라벨을 만들지 않습니다.
- 서버가 저장한 `schema_version=3`, `ranking_version=rules-v2` 스냅샷만 사용합니다. 요청 내 후보 ID/순위 중복, `hard_constraints != pass`, 잘못된 특징 값, 예산/거리/도보 조건 위반 등이 있으면 해당 요청 전체를 제외합니다. 클라이언트가 특징/라벨 JSON을 업로드하는 API는 없습니다.
- 필터 근거는 **당시 서버 스냅샷**을 사용합니다. 지금 식당이 영업 중인지 재검색하거나 과거 근거일을 오늘로 고치지 않습니다. 오프라인 모델 출력으로 새 방문의 안전성을 판단하지 마세요.
- 노출 이벤트와 단일 식당 선택이 모두 있는 요청만 사용합니다. 선택한 후보는 `1`, 같은 요청에서 표시했으나 선택하지 않은 후보는 `0`입니다. 선택 없는 요청·길찾기/상세보기만 한 요청은 음성으로 간주하지 않습니다.
- 같은 식당을 여러 번 누른 중복은 한 라벨로 취급합니다. 각 분할의 기준 시점까지 서로 다른 식당을 선택했거나 선택 식당을 거절한 충돌 기록, 노출보다 먼저 발생한 선택은 제외합니다. 이미 기록된 데이터를 임의 수정하지 않습니다.
- 식당 1곳만 표시한 요청은 선택지 사이의 순위 비교가 불가능하므로 제외합니다. 제외 사유별 개수를 보고서에 남깁니다.

학습·평가 정책:

- 특징: 가격, 직선거리, 확인된 도보 시간, 예산 대비 가격, 소프트 일치 수, 근거 완성도/당시 나이, 날씨 보조 점수와 누락 표시, 카테고리, 한국 시간대/요일. **식당 ID·이름, 원문·좌표·세션 ID, 선택 후 정보, 기존 노출 순위는 입력 특징에서 제외**합니다. 기존 순위는 기준선/동점 결정용으로만 사용합니다.
- 기존 의존성의 `DictVectorizer → RandomForestClassifier`를 사용합니다. 인코더도 학습 구간으로만 fit합니다. 트리 100개, 깊이 6, 최소 리프 2, seed 42, 단일 CPU worker로 고정하며 이번 버전은 튜닝하지 않습니다.
- `selection-rf-v2`는 **라벨 유무와 무관하게 비교 가능한 안전 스냅샷의 요청 시각**으로 약 80%/20% 경계를 고정합니다. 한 요청의 후보와 같은 시각 요청을 나누지 않습니다. 학습 라벨은 평가 시작 시각 이전 이벤트만 다시 읽어 복원합니다. 나중의 거절/재선택 때문에 과거 학습 후보가 사라지거나 라벨이 바뀌지 않습니다. 당시 선택 기록이 없던 요청은 학습에서 제외합니다. 보고서 `split.purged_delayed_labels`는 이 경계에서 선택 누락/지연/충돌로 제외한 과거 요청 수이며, `counts`는 실행 시점의 전체 진단이라 학습 건수와 다를 수 있습니다.
- 비교는 동일한 평가 후보에서 `NDCG@3`, `MRR`, `top1_agreement`(실제 선택 후보와 1위의 일치율)를 계산합니다. RF 점수가 같으면 원래 규칙 순서를 보존합니다. 후보별 규칙 순위, RF 순위, 선택 점수, 실제 라벨도 기록합니다.
- **Top 1 일치율은 서비스 선택률/CTR이 아닙니다.** 선택이 있었던 요청만 평가하고 기존 노출/위치 편향이 남습니다. 익명 세션이 시간 분할 양쪽에 있을 수 있으며 신규 사용자 일반화 평가도 아닙니다. RF 점수는 보정되지 않은 모델 출력입니다.
- 유효 요청 10건 이상, 분할 후 학습 6건/평가 2건 이상일 때만 실행합니다. 이는 작은 실습의 기술적 하한이지 충분한 평가 표본 수가 아닙니다. 부족하면 `insufficient_data`, 종료 코드 `2`이며 모델/성능 수치를 만들지 않습니다.

## 메뉴 근거 점검과 제외 사유 구분

추천 응답의 `diagnostics`에 `rejection_version: evidence-v1`, `count_unit: reason_occurrences`, `category_counts`, `rejections`를 추가했습니다. 기존 `rejected` 문자열 집계는 호환용으로 유지하지만, 화면은 구조화된 분류를 사용합니다.

| 분류 | 예시 | 필수 조건 처리 |
| --- | --- | --- |
| `constraint_mismatch` · 조건 불충족 | 유효한 가격이 예산 초과, 거리/도보 상한 초과, 유효한 휴무 확인 | 제외 |
| `missing_evidence` · 근거 부족 | 메뉴/가격 누락, 알레르기·교차접촉/식단/필수 분위기 자료 없음, 자료 형식 오류, 미래 기준일 | 제외 |
| `expired_evidence` · 자료 만료 | 90일 초과 메뉴/특성 근거, 유효 시간이 지난 영업 확인 | 제외·재확인 필요 |

```json
{
  "category": "missing_evidence",
  "field": "allergens",
  "code": "allergy_evidence_missing",
  "message": "땅콩 알레르기·교차접촉 확인 근거 없음",
  "place_id": "123",
  "menu_name": "예시 메뉴",
  "unit": "menu"
}
```

위 객체는 응답 형식 예시이지 실제 식당 자료가 아닙니다. 연결된 메뉴 자체가 없는 장소는 `code=menu_missing`, `unit=place`, `menu_name=null`입니다. 깨진 SQL JSON이나 행 키와 내용이 다른 자료도 유효 근거로 사용하지 않고 `menu_invalid`로 제외합니다. 공백뿐인 메뉴명/출처 제목, boolean 가격, 문자열로 적힌 교차접촉 확인값도 유효한 확인 자료로 취급하지 않습니다.

- 집계는 **검사 사유 건수이지 식당 수가 아닙니다**. 한 메뉴가 여러 사유에 포함될 수 있고, 앞 단계에서 제외되면 뒤 단계는 검사하지 않습니다. 미검사 조건을 통과했다고 표시하지 않습니다.
- 오래된 가격은 예산 초과로 단정하지 않고 자료 만료로 분류합니다. 미래 날짜는 만료가 아니라 근거 기준일 오류입니다. 알레르기 기록이 있어도 교차접촉 확인이 없으면 근거 부족입니다.
- 선택적 선호의 자료 누락/만료는 추천 제외 사유가 아닙니다. 카드에 별도 **선택적 선호 미확인** 안내를 표시하며 선호 충족 점수는 주지 않습니다. 필수로 지정한 선호는 같은 상황에서 제외됩니다.
- 결과 없음은 “확보한 자료로 모든 필수 조건을 확인한 추천을 만들지 못했다”고 안내하고 분류별 건수를 보여줍니다. 장소 조회 자체가 0건인 경우도 별도 안내합니다. 일부 추천이 있어도 제외 사유를 접어서 확인할 수 있습니다.
- RAG 생성 전후 근거·영업 기록 재검사도 같은 분류를 사용합니다. 같은 메뉴 가격 출처가 설명과 예산 근거에 중복되어 있어도 동일 출처의 만료를 중복 집계하지 않습니다.
- 자동 조건 완화, 알레르기 근거 없는 통과, 근거 기준일 갱신은 추가하지 않았습니다. URL·날짜·형식 검사만으로 출처 원문의 진실성이나 현재 판매 가격까지 자동 검증한 것으로 간주하지 않습니다.

9/9 검증: 백엔드 **66개 테스트·JS 검사 통과**. 세 분류, 오래된 가격, 알레르기/교차접촉, 미래 근거, 선택적 선호, 잘못된 SQL 기록, 생성 중 만료, 사유 건수와 식당 수 구분, 화면 텍스트/XSS를 검사했습니다. 실제 DB 7개 메뉴를 읽기 전용 점검한 결과 메뉴명·가격 형식/존재·90일 유효기간 기준 5개 통과, 2개 자료 만료였습니다. 이는 모든 식단/알레르기 조건 통과나 웹 원문/현재 가격 재확인을 뜻하지 않습니다. 실제 DB·CSV·기준일은 변경하지 않았습니다.

## 9/9 코드 검토와 수정 사항

현재 요청 경로와 학습 코드를 검토하고 다음 문제를 회귀 테스트로 고쳤습니다. 전체 보안 감사나 실제 모델 성능 검증을 완료했다는 뜻은 아닙니다.

| 문제 | 수정·검증 |
| --- | --- |
| 과거 분류기의 정답 유출 | `RandomForestClassifier.py`에서 정답 카테고리로 병합하던 통계 특징 제거. 정답/주문 수를 바꿔도 입력 특징이 동일한지 검사 |
| RF 시간 분할의 미래 피드백 참조 | `selection-rf-v2`에서 스냅샷 시간으로 경계를 고정하고 당시 이벤트만으로 학습 라벨 복원. 미래 거절/선택 누락에도 학습 집단과 예측이 유지되는지 검사 |
| 생성 초안과 확정 입력의 검증 불일치 | Qwen 출력에도 기존 `ConfirmedConstraints` 검증 재사용. 중복 조건/장소 길이 초과/과도한 미지원 조건은 초안 발급 전 차단 |
| 장소 API 비정상 응답이 500으로 전파 | 공통 `kakao_get()`에서 JSON 객체/문서/좌표/페이지 형식 검사. 비정상 응답은 키·URL 없는 503, 도보 조회 실패는 기존 미확인 정책 유지 |
| 미지원 조건 원문이 DB에 잔존 | 스냅샷에서 `unknown_terms` 제거, 재질문 메시지는 일반 문구로 저장. 화면의 사용자 확인 내용은 유지하고 DB에는 개수만 기록 |
| 미설정 지도 키의 하드코딩 대체 | 숨은 기본 키 제거. 키가 없으면 SDK를 호출하지 않고 기존 목록 대체 화면 사용 |
| 과거 회귀 CV 점수의 과대 해석 | 전체 집계에서 만든 참고 라벨에 대한 “최적 MSE” 출력 제거. 고정 파라미터 학습만 제공하며 미래 선택 평가와 명확히 구분 |

검증: **백엔드 61개 테스트·JS 검사 통과**, 의존성 검사 통과, 합성 40건 RF v2 학습/비교 실행 완료. 실제 선택 데이터 성능은 여전히 미검증입니다. 기존 `.env`·메뉴 CSV·실제 DB·`model/` 바이너리는 변경하지 않았습니다. 이전에 저장된 스냅샷을 자동 삭제/수정하지 않았고, 현재 DB에서 `unknown_terms`가 비어 있지 않은 과거 기록은 0건이었습니다.

`.github/workflows/tests.yml`에 Python 3.11 + Node 22의 push/PR 검사를 추가했습니다. 기존 모델 의존성까지 설치하여 RF 테스트가 선택 의존성 누락으로 건너뛰어지지 않도록 구성했습니다. 실제 API 키나 Ollama 없이 모의 테스트와 합성 학습을 실행합니다. **로컬 동등 명령은 통과했지만 GitHub Actions 실행은 아직 확인하지 않았습니다.**

채용 담당자에게는 다음 한계도 숨기지 않고 설명해야 합니다.

- 과거 분류 모델의 기존 바이너리는 정답 유출 특징을 포함했을 수 있으며 이번에 재학습하지 않았습니다. 웹 추천에서는 이 분류기를 사용하지 않습니다. 선택적 날씨 회귀 바이너리도 미래 선택 성능을 입증한 모델이 아닙니다.
- Qwen의 원문 근거/타입 검증은 의미 해석의 정확성을 보증하지 않습니다. 9/8 자연어 평가 수치는 당시 버전의 기록이며 이번 방어 코드 변경 후 실제 40문장 평가를 다시 수행한 값이 아닙니다.
- RAG는 검토된 SQL 기록의 문장을 선택하는 제한형 RAG이고, 웹 원문 진위를 자동 검증하는 시스템이 아닙니다. 확보한 식단/알레르기/영업 자료도 제한적입니다.
- RF 비교는 노출된 2~3곳에 한정되고 위치/노출 편향이 남습니다. 합성 실습 점수를 사용자 선택률 향상으로 소개하지 않습니다.
- 로컬 단일 프로세스 시연 범위입니다. 공개 배포 수준의 인증, 분산 동시성, 부하/운영 보안 검증은 포함하지 않았습니다.

## 남은 6일 포트폴리오 일정

목표는 로컬 시연 가능한 작은 프로젝트입니다. **대규모 메뉴 수집·크롤러·벡터 DB·임베딩·멀티에이전트·장기 기억·전국 지원·공개 배포는 제외**합니다. 기존 데이터의 누락·유효기간 검사는 유지합니다.

| 예정일 | 작업 | 완료 기준 |
| --- | --- | --- |
| 9/8~9/9 | 해석/검색 분리·확인 UI·최소 LangGraph | 이번 변경으로 구현. 로컬 환경에서 데모 흐름 재현 |
| 9/10 | 기존 자료로 작은 2-step RAG | 이번 변경으로 제한형 RAG 구현. 근거 문장/출처 검증 실패 시 기존 템플릿 사용 |
| 9/11 | RandomForest 학습·규칙 정렬 비교 파이프라인 | 구현·합성 실행 완료. 노출된 하드 필터 통과 후보로 비교하며 실제 데이터 성능은 미검증 |
| 9/12 | 통합 검증·실패 시연 | 정상/사용자 수정/결과 없음/모델 장애, 근거 없는 사실과 제약 위반 검사, 지연 측정 |
| 9/13 | README·데모·포트폴리오 정리 | 실행 방법, 구조, 실제 측정값, 데이터/모델 한계, 시연 영상 |

현재는 **SQL 근거 기반 제한형 RAG와 선택 예측 RF 오프라인 학습·비교를 구현**했습니다. 실제 선택 데이터가 없어 운영 RF는 학습하지 않았습니다. 가격·거리·하드 필터·운영 후보 순위는 계속 규칙 코드가 결정하고 설명 모델이 바꾸지 못하게 합니다.
행동 데이터가 부족하면 RF의 실제 선택률 개선은 검증 불가로 표기합니다. 합성/수작업 데모 라벨은 실제 사용자 선택과 분리하고, 기존 날씨 모델을 선택 예측 모델로 소개하지 않습니다. 비교가 불충분하면 기본 추천은 규칙 정렬을 유지합니다.
정상 시연도 최대 3곳이며 실제 확인 후보가 적으면 1~2곳/결과 없음이 맞습니다. 자료를 늘리거나 기준일·성분 정보를 만들어 3곳을 채우지 않습니다.
