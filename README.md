# WHERE FOOD — 근거 기반 식사 추천 MVP

Flask + Vanilla JS로 자연어 → 제약 JSON → 실제 장소/메뉴 조회 → 규칙 필터 → 최대 3곳 → 선택 기록을 연결합니다.
자연어 해석은 **Ollama + Qwen3.5 9B 로컬 모델만** 사용합니다. 숫자·필수 조건 판정·정렬·설명은 서버 코드가 수행합니다.
OpenAI 호출 코드와 SDK 의존성을 제거했습니다. 공용/프로젝트 전용 OpenAI 키가 있어도 사용하지 않으며, 외부 LLM 자동 전환도 없습니다.

구조: 브라우저 → Flask → 로컬 Ollama 제약 추출 → Pydantic/원문 검증 → 카카오 장소·경로 + SQLite 메뉴 근거 → 규칙 필터·최대 3곳 → 행동 저장.
**LLM만 로컬**입니다. 카카오 장소·지도·경로, 선택적 날씨 조회와 웹 폰트 등은 네트워크를 사용합니다.

## 실행

Python 3.11 이상을 사용합니다. 기존 `venv`는 Python 3.9/3.11 경로가 섞여 있어 새 `.venv`를 사용합니다.

### 1. Ollama와 모델 준비

[Ollama](https://ollama.com/download)를 설치합니다. macOS에서는 GPU 사용을 위해 네이티브 앱/CLI 실행을 권장합니다.
터미널 하나에서 클라우드 기능을 끈 로컬 서버를 실행합니다. 이미 Ollama가 해당 포트에서 실행 중이면 서버를 중복 실행하지 말고 해당 실행 방식에 클라우드 차단 설정을 적용한 후 재시작하세요.

```sh
OLLAMA_NO_CLOUD=1 OLLAMA_HOST=127.0.0.1:11434 OLLAMA_NUM_PARALLEL=1 OLLAMA_MAX_LOADED_MODELS=1 ollama serve
```

다른 터미널에서 모델을 준비합니다. `qwen3.5:9b`는 약 6.6GB 다운로드이며 실행 메모리는 추가로 필요합니다. 기존 모델을 삭제할 필요는 없습니다.

```sh
OLLAMA_HOST=127.0.0.1:11434 ollama pull qwen3.5:9b
curl --noproxy '*' http://127.0.0.1:11434/api/tags
```

macOS Ollama 앱으로 실행하는 경우 `launchctl setenv OLLAMA_NO_CLOUD 1` 설정 후 앱을 재시작합니다.
Flask의 `.env`에 `OLLAMA_NO_CLOUD=1`만 추가해도 **이미 실행 중인 Ollama 서버에는 적용되지 않습니다**.
모델 이름과 URL은 코드에 고정되어 `OLLAMA_HOST`, `OLLAMA_MODEL`, OpenAI 관련 환경변수로 바뀌지 않습니다.
로컬 HTTP 클라이언트는 환경 프록시·자동 인증·리디렉션을 사용하지 않습니다. `:cloud` 모델이나 외부 LLM API로 재시도하지 않습니다.

### 2. Flask 실행

프로젝트 루트에서 실행합니다. 이미 `.venv`가 있으면 생성 단계는 생략할 수 있습니다.

```sh
python3.11 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python scripts/import_menu_data.py
.venv/bin/python app.py
```

http://127.0.0.1:8000 에서 실행됩니다. `.env`에 `.env.example`의 설정을 반영하세요. 기존 키를 덮어쓰지 마세요.

- 공용 `OPENAI_API_KEY`는 사용하지 않습니다. 기존 환경변수와 `.env`의 키도 변경하지 않습니다.
- 이전 `WHERE_FOOD_ENABLE_OPENAI`, `WHERE_FOOD_OPENAI_API_KEY`, `WHERE_FOOD_OPENAI_MODEL` 설정은 더 이상 읽지 않습니다.
- `WHERE_FOOD_OLLAMA_TIMEOUT_SECONDS`: 기본 `120`, 허용 범위 `1~300`. 모델 첫 로딩이 느린 경우에만 조정합니다. 연결 제한은 3초입니다.
- `KAKAO_REST_API_KEY`: 장소·좌표·도보 경로 조회용.
- `KAKAO_JAVASCRIPT_KEY`: 지도 표시용 공개 앱 키. 카카오 개발자 설정에 사용하는 로컬 도메인을 등록하세요.
- `WEATHER_API_KEY`: 선택. 날씨 실패는 식당 추천을 막지 않습니다.
- `FLASK_SECRET_KEY`: 지속적인 랜덤 값. 미설정 시 프로세스마다 임시 키가 생겨 재시작 후 이전 세션 기록에 접근할 수 없습니다. 운영/여러 worker는 동일한 값 필요.
- `DATABASE_PATH`: 기본 `instance/where_food.db`. `instance/`는 Git에서 제외합니다.
- `COOKIE_SECURE=1`: HTTPS로 서비스할 때 설정합니다.

`GET /api/health`는 `/api/tags`로 서버 연결·정확한 모델 설치 여부를 확인하여 `parser.provider`, `parser.model`, `parser.ready`, 모델 `digest` 또는 실패 코드를 반환합니다. 추론을 실행하거나 모델을 로딩하지 않습니다.
`ready=true`는 모델 설치 확인이지 메모리 여유·추론 성공·의미 정확성을 보증하지 않습니다. 카카오 키는 설정 여부만 표시합니다.
`.env` 설정을 변경했다면 Flask 서버를 재시작하세요.

### 3. 식당 API 없이 로컬 추출만 확인

```sh
.venv/bin/python scripts/evaluate_parser.py --query '강남역에서 도보 10분, 1만 5천 원 이하, 얼큰한 국물인데 땅콩은 빼고 조용한 곳'
.venv/bin/python scripts/evaluate_parser.py
```

첫 명령은 검증된 제약 JSON을 출력합니다. 두 번째는 수작업 정답 8문장에 대해 필드별 불일치, 통과 수, p50/p95 시간을 출력합니다.
정답 비교에서 목록 순서만 무시하고, 누락·임의 추가·알레르기 오인식은 실패로 집계합니다. 실패가 있으면 종료 코드 1입니다.
모델 로딩 시간은 첫 사례 시간에 포함됩니다. 이것은 시작용 스모크 평가이지 8문장으로 일반적인 한국어 정확도를 입증하는 벤치마크가 아닙니다.
이 스크립트는 **카카오·날씨 API를 호출하지 않고 앱 DB에 쓰지 않습니다**. `--limit 1`로 한 문장부터 확인할 수 있습니다.

기존 날씨 모델의 카테고리 힌트를 켜려면 추가 설치합니다.

```sh
.venv/bin/python -m pip install -r requirements-model.txt
```

기존 모델은 2019–2020년 집계 기반 참고 힌트로 남겨두었습니다. 실제 식당 순위에는 사용하지 않습니다.
학습·그래프 스크립트와 모델 파일은 보존했으며, Selenium과 공용 `result.png` 생성은 웹 요청 경로에서 제거했습니다.

초기 데이터는 메뉴명·가격 사실과 출처만 수록했습니다. 사진이나 전체 소개글은 포함하지 않았습니다.
출처 페이지에는 이용 조건이 있으므로 상용 데이터 확장은 사용 가능한 제공처/매장 확인 자료로 진행하세요.
90일보다 오래된 근거는 재확인 대상으로 제외하므로 장모님밥상은 현재 확정 추천에서 제외됩니다.
현재 데이터에는 땅콩 미사용·알레르기 교차접촉·조용함 근거가 없습니다.
따라서 예제의 땅콩 제외 조건은 결과 없음이 정상이며, 일반 메뉴로 자동 완화하지 않습니다.

먼저 “강남역에서 1만 5천 원 이하 식당”으로 확인하고, 식재료/분위기 근거를 확보한 후 더 복잡한 조건을 검증하세요.
메뉴 데이터는 자동 수집·자동 갱신하지 않습니다.

CSV의 `menu_evidence`는 다음 JSON을 셀 안에 넣습니다. `observed_on`은 실제 확인일 또는 출처의 사실 기준일입니다.

```json
{
  "title": "매장 공식 메뉴 또는 확인 기록",
  "url": "https://example.com/actual-menu-evidence",
  "observed_on": "2026-09-07",
  "excerpt": "해당 메뉴명과 1인 메뉴 가격을 입증하는 짧은 원문"
}
```

`tags`, `absent_ingredients`, `atmosphere`는 각각 `[{"term": "...", "evidence": {...}}]` 형식입니다.
`allergy_checks`는 여기에 `cross_contact_checked`가 추가됩니다. 식당의 해당 성분 미사용과 교차접촉 관리에 대한 명시적 확인 기록이 있을 때만 true입니다.
재료 목록에 이름이 없다는 사실, 메뉴명에서의 추정, 블로그 추측은 미사용/알레르기 근거가 아닙니다.
빈 배열은 **미확인**입니다. 단순 기피 재료와 알레르기는 구분하고, 알레르기는 방문 전 재확인을 안내합니다.
실제 가격이 없는 경우 `price_krw`를 비워 두면 저장할 수 있지만 추천 후보로는 통과하지 않습니다.

데이터 반영은 `(place_id, menu_name)` 단위 upsert이며 다른 메뉴·사용자 기록은 삭제하지 않습니다.
원하는 경우 `--database /path/to/file.db`로 별도 DB를 지정할 수 있습니다.

## API 계약

`POST /api/recommend`:

```json
{
  "query": "강남역에서 도보 10분, 1만 5천 원 이하",
  "lat": null,
  "lon": null,
  "origin_place_id": null
}
```

문장 내 위치가 우선입니다. 위치 결과가 여러 개면 `clarification_required`와 `location_options`를 반환합니다.
선택된 ID는 다음 요청의 `origin_place_id`로 보내며 서버는 다시 조회한 후보와 대조합니다.
장소 없는 문장에는 lat/lon이 필요합니다. 클라이언트가 추출 JSON, 금액, 추천 순위를 직접 확정하도록 허용하지 않습니다.

응답에는 `request_id`, `parser`(공급자·모델·파서 버전), `constraints`, `origin`, `status`, `recommendations`, `diagnostics`가 들어갑니다.
추천 항목에는 장소 정보, 대표 메뉴·가격·출처, 충족 조건의 근거, 미확인 선호, 조회 시각, 경로가 들어갑니다.

상태:

- `ok`: 3곳 확인
- `partial`: 1~2곳 확인. 조건 미충족 식당으로 3곳을 채우지 않음
- `no_results`: 검색 범위/확보 데이터에서 확인된 후보 없음
- `clarification_required`: 위치 선택·모호하거나 현재 지원하지 않는 조건 확인 필요

HTTP 오류는 JSON의 `error`, `code`로 반환합니다.

| HTTP / code | 뜻 / 조치 |
| --- | --- |
| 400 / `invalid_input` | 입력 형식 확인 |
| 422 / `parse_failed` | JSON 불완전·스키마 오류·원문/숫자 불일치. 문장을 명확히 수정 |
| 429 / `parser_busy` | 같은 Flask 프로세스의 이전 추론이 진행 중. 완료 후 다시 시도 |
| 503 / `ollama_unavailable` | Ollama 실행·버전·메모리 확인 |
| 503 / `ollama_model_missing` | `ollama pull qwen3.5:9b` 실행 |
| 503 / `parser_not_configured` | 프로젝트 전용 timeout 설정 확인 |
| 504 / `ollama_timeout` | 모델 로딩·메모리·timeout 확인. 자동 재시도 없음 |

기존 장소·경로·DB 장애도 503으로 반환합니다. Ollama는 `think=false`, `temperature=0`, 컨텍스트 8192, 출력 상한 2048토큰으로 호출합니다.
최종 완료된 JSON만 처리하고, 잘린 출력·중복 원문 근거·잘못된 숫자를 통과시키지 않습니다. 설정은 문장 단위 추출의 초기값이며 품질·속도 측정 후 조정하세요.
추론 후 모델은 기본 5분간 메모리에 유지합니다. 입력 수정으로 브라우저 요청을 취소해도 서버 추론이 즉시 중단되는 것은 아닙니다.

`POST /api/events`:

```json
{
  "id": "이벤트 UUID",
  "request_id": "추천 응답의 UUID",
  "event_type": "restaurant_selected",
  "place_id": "실제로 노출된 식당 ID"
}
```

종류는 `recommendations_viewed`, `restaurant_selected`, `restaurant_rejected`, `detail_clicked`, `directions_clicked`입니다.
노출 이벤트는 place_id=null, 나머지는 실제 추천한 장소만 허용합니다. 순위와 세션 ID는 서버에서 결정합니다.
같은 이벤트 ID 재시도는 중복 저장하지 않습니다. 다른 세션/다른 요청의 식당에 대한 임의 선택 기록은 거부합니다.
원문·정확한 시작 좌표·좌표가 들어간 경로 링크는 저장 스냅샷에서 제거합니다. 메뉴·추출 조건·노출 후보·순위·출처·행동은 보존합니다.
클릭은 방문/주문이나 최종 선택의 정답으로 자동 간주하지 않습니다.

## 필터·정렬 정책

1. 근거 날짜(현재 기준 90일), 가격 존재 여부 확인
2. 예산, 제외 음식/재료, 알레르기와 필수 특성 검증
3. 요청된 직선거리 상한 검사
4. 도보 조건이 있으면 실제 경로 API의 초 단위 예상 시간을 검사. 600초는 통과, 601초는 제외
5. 같은 식당의 통과 메뉴 중 선호 일치가 많고 저렴한 메뉴 한 개 선택
6. 선호 일치 수 → 도보 시간(도보 미요청 시 직선거리) → 가격 → 장소 ID 순 정렬

검색은 기본 2km, 가까운 음식점 최대 45곳 + 현재 메뉴 카탈로그 최대 6개 상호의 검색 결과(각 5개)를 합칩니다.
검색·태그는 범위가 제한된 MVP입니다. 데이터가 늘면 지역별 카탈로그 인덱스와 검색 재현율을 먼저 개선하세요.
가격·거리 등의 숫자는 원문 단위를 서버에서 다시 계산합니다. 스키마 형식이 맞아도 LLM의 의미 추출 정확성은 별도 평가가 필요합니다.
지원하지 않는 영업시간·채식·복합 OR·전체 인원 예산 등은 파서가 `unknown_terms`로 남겨 재질문합니다. 자동 조건 완화는 하지 않습니다.
알레르기 기록은 안전 보증이 아닙니다. 누락 근거를 만들어 추천하지 않습니다.

## 앞으로의 개발 순서

### 1. 제약 추출 평가와 사용자 확인 (최우선)

- 시작용 8문장을 50~100개로 확장: 금액 표기, 이중 부정, 제외/알레르기, 조용함 필수/선호, 장소 중복, 지원하지 않는 조건, 프롬프트 주입.
- 프롬프트 수정용과 최종 검증용 문장을 분리하고 모델 digest·프롬프트 버전·추론 설정을 함께 기록.
- JSON 형식 성공률과 필드 의미 정확도를 따로 측정. 특히 알레르기·제외·예산 누락은 별도 실패로 집계.
- 첫 로딩/재사용 p50·p95와 메모리를 실측. 안전 조건 테스트에서 발견한 오류를 해결하기 전 실사용으로 확대하지 않기.
- 현재 UI는 추출 조건을 보여주지만 검색 전 확인 단계는 없음. 다음에는 필수 조건을 사용자가 확인/수정한 뒤 검색하는 흐름 추가.
- 현재 '조용한'은 선호이고 '반드시 조용한'은 필수. 이 정책을 화면에서 명확히 보여주고 필수 여부를 사용자가 선택하도록 개선.

### 2. 좁은 지역의 실제 메뉴·성분·분위기 근거 확보

- 우선 강남역 한 지역에서 식당 20~30곳, 메뉴 50~100개를 목표로 확보. 규모 자체가 품질 기준은 아님.
- 매장 공식 메뉴·직접 확인 기록으로 메뉴별 가격과 성분, 확인 시각, 출처를 수집. 지점 ID를 정확히 연결.
- 성분 미사용과 교차접촉 기록은 구분하고 없으면 미확인 유지. 알레르기 안전을 보증하지 않기.
- '조용함'은 방문 시간대·측정/리뷰 근거·불확실성을 포함하도록 데이터 모델 보완.
- 최신 근거로 갱신한 뒤 importer 실행. 출처 방문일만 갱신하여 오래된 가격을 최신처럼 만들지 않기.
- 목표 문장에서 실제로 충족을 확인한 식당이 3곳 미만이면 적은 수 또는 결과 없음이 정상. 모델로 빈 데이터를 채우지 않기.

### 3. 근거 검색 확대와 2-step RAG

- 지금은 장소 API + 구조화 메뉴 SQL 조회 + 템플릿 설명이며 벡터 RAG는 아직 없음.
- 문서가 늘면 식당/지점/메뉴 식별자로 관련 근거를 검색하고, 검색된 자료 안에서만 설명을 생성하는 두 단계 추가.
- 금액·거리·알레르기 판정과 Top 3 순위는 계속 코드가 결정. 문서 내용도 지시가 아닌 데이터로 처리.
- 먼저 SQL/FTS 검색의 누락률을 측정하고 의미 검색이 실제로 필요한 경우에만 임베딩/벡터 저장소 도입.
- 현재 검색은 카탈로그 6개 상호 보강 한도가 있어 20~30곳으로 확장할 때 지역별 DB 후보 조회를 먼저 개선.

### 4. 재질문·조건 완화와 대화 상태

- 추출 → 사용자 확인 → 검색 → 부족한 조건 안내 → 사용자가 승인한 변경만 적용.
- 처음에는 Flask 세션/DB로 필요한 상태만 유지. 위치 재선택 시 같은 문장을 재추론하는 현재 비용도 개선.
- 알레르기·제외 조건을 자동 완화하지 않기. 분기/재개/재시도가 실제로 복잡해질 때 LangGraph 검토.

### 5. 선택 데이터와 학습 모델

- 이미 노출·선택·제외·상세·길찾기를 기록함. 조회/길찾기와 최종 선택/방문을 같은 라벨로 취급하지 않기.
- 현재 저장하는 파서 버전·모델명·근거 기준일에 모델 digest, 랭킹 특징을 더해 원문·정밀 위치 없이 재현성을 확보.
- 학습 데이터가 쌓이면 시간·사용자 단위 분리로 누수를 막고 현재 규칙 순위와 비교.
- RandomForest는 필수 필터를 통과한 후보 내 실제 선택 예측에만 사용. 클릭하지 않은 모든 후보를 싫어한 정답으로 단정하지 않기.

### 6. 배포 전 운영 점검

- 현재는 개발용 Flask 서버와 프로세스 내 단일 추론 잠금. 여러 worker에서는 공유 대기열/동시 실행 제한 필요.
- 공개 배포 전 인증·요청 제한·로그 보존/삭제 정책·DB 백업·오류 관측 추가. Ollama 포트를 인터넷에 공개하지 않기.
- 배포 서버의 127.0.0.1은 개발자 맥이 아님. 배포할 때는 동일 호스트 로컬 추론 또는 별도로 승인한 사설 추론 서버 구성을 결정.
- 사용하지 않는 거대 프레임워크·벡터 DB·재학습 작업은 현재 의존성에 미리 추가하지 않음.
